# Build Log

Running notes on anything that broke, surprised, or needed a non-obvious fix while building.
This feeds the README's design-decisions section later — kept live, not reconstructed after the fact.

## Phase 1 — Backend + Postgres

- **Docker Desktop wasn't running** when the first `docker compose up` was attempted (`failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`). Had to launch Docker Desktop and poll `docker info` until the engine responded before compose would work. Environmental, not architectural, but worth remembering if the "one command works" README claim is tested on a fresh machine — Docker Desktop needs to actually be running first.

- **`useradd` + `pip install --user` in a multi-stage build silently breaks `PATH`.** The builder stage runs `pip install --user` (so runtime doesn't need a compiler toolchain), which puts console-script entry points — `uvicorn` included — under `~/.local/bin` of whatever user ran it. Copying `/root/.local` into the runtime stage's non-root home (`/home/app/.local`) is not enough by itself: that directory isn't on `PATH` for the non-root user, so `CMD ["uvicorn", ...]` would fail with "executable not found" unless `PATH` is explicitly extended (`ENV PATH=/home/app/.local/bin:$PATH`) in the runtime stage. Easy to miss because it works fine under a root-only single-stage build.

- **`${VAR}` vs `$${VAR}` in compose healthcheck `CMD-SHELL` strings.** Docker Compose interpolates `${...}` at *compose-parse time* using its own variable resolution (which happens to include the project's `.env` file). Writing the Postgres healthcheck as `pg_isready -U ${POSTGRES_USER}` would still "work" today only because compose's interpolation and the container's actual runtime env (from `env_file:`) happen to agree. Escaping as `$${POSTGRES_USER}` forces the substitution to happen inside the container's shell at healthcheck-run time instead, using the real runtime environment — the correct behavior, and the one that keeps working if the two values ever diverge (e.g. secrets injected by an orchestrator instead of a literal `.env` file). Chose to do this correctly now rather than let it pass by coincidence.

- **Schema source of truth: `init.sql`, not Alembic, not `Base.metadata.create_all()`.** SQLAlchemy models in `models.py` describe the same `links`/`clicks` shape as `db/init.sql`, but the app never calls `create_all()` — Postgres's `docker-entrypoint-initdb.d` mechanism runs `init.sql` once against the empty data directory, and the ORM only ever queries against that pre-existing schema. Two sources of truth (raw SQL + ORM `create_all`) would drift silently; picking one avoids that. Alembic was the other option per the plan but is more machinery than a two-table schema needs at this stage.

- **Named volume + Postgres healthcheck + `depends_on: condition: service_healthy` were pulled forward from Phase 5 into Phase 1** (a deliberate deviation from the section 8 build order, confirmed with the user before doing it). Without them, the backend can start and crash-loop before Postgres accepts connections, and `docker compose down` (without `-v`) would silently wipe all data since there's no durable volume. Verified in this phase: a full `docker compose down` + `up` cycle (which removes and recreates both containers) preserved the one link left in the table — proof the named volume, not container survival, is what's holding the data.

- Verified the non-root user is real, not just declared: `docker compose exec backend id` returns `uid=1000(app) gid=1000(app)`, not root.

## Phase 2 — Redis (redirect cache + rate limiting)

- **Cache-hit path still needs a Postgres write, so caching doesn't mean "no DB traffic."** The redirect endpoint's whole point is avoiding a DB round trip to *resolve* `short_code -> long_url`, but every redirect — hit or miss — still has to write a `clicks` row for analytics, which is itself a DB round trip. Kept the redirect response from waiting on that write by recording it as a FastAPI `BackgroundTask`, using a single `INSERT INTO clicks (...) SELECT id, ... FROM links WHERE short_code = ...` so the click write doesn't need the link's id looked up separately in Python first (which would have meant hitting Postgres again just to get an id, on top of the cache hit).

- **Fixed-window rate limiting counts *attempts*, not just *allowed* requests.** `check_rate_limit` does `INCR` before comparing against the limit, so a burst of 7 requests against `RATE_LIMIT_MAX=5` shows the Redis counter at 7 (or 8, if an earlier request already shared that 60-second wall-clock bucket) while only the first 5 succeed. Confirmed with `redis-cli GET`/`TTL` on the `ratelimit:create:{ip}:{bucket}` key — this is expected fixed-window behavior (a request that gets rejected still "spends" a slot), not a bug, but worth stating explicitly since it's the kind of thing that looks wrong at first glance in the Redis data.

- **Real inconsistency, not hypothetical: cache invalidation only happens through the API.** While cleaning up test data I deleted rows directly with `DELETE FROM links` in `psql` instead of calling `DELETE /api/links/{code}`. The app's delete/update handlers call `cache.invalidate_cached_url()`, but a direct SQL delete bypasses the app entirely — `redis-cli KEYS "link:*"` afterward still showed `link:rtest1` with ~24h left on its TTL, meaning a redirect to a since-deleted link would have kept "working" (serving a stale cached URL) until the TTL expired. This is the textbook cache-invalidation gotcha in a write-through design: the cache is only as consistent as the write path is disciplined. Worth a line in the README — any future direct DB access (manual fix, migration, admin script) needs to also clear the corresponding Redis key, or shorten the TTL if that's an accepted risk.

- Redis is run with `--save "" --appendonly no` (persistence disabled) — deliberate, since it's used purely as an ephemeral cache/counter store; losing it just means the next redirect is a cache miss and rate-limit windows reset, not data loss.

- `/health` now also does `await cache.redis_client.ping()`, so the backend's Dockerfile `HEALTHCHECK` fails (and compose reports `unhealthy`) if Redis becomes unreachable, not just Postgres.

## Phase 3 — Frontend (create-link form + basic analytics)

- **`npm ci` needs a real `package-lock.json` — there was no Node.js on this machine to generate one.** The frontend build failed immediately (`npm ci` refuses to run without an existing lockfile). Rather than fall back to `npm install` in the Dockerfile (which would make builds non-reproducible — floating to whatever versions satisfy the range on each build), generated a real lockfile once via a throwaway container: `docker run --rm -v <frontend>:/app -w /app node:20-alpine npm install --package-lock-only`. `--package-lock-only` avoided also dumping `node_modules` onto the host through the bind mount. The committed lockfile is what makes `npm ci` — and therefore reproducible builds — possible at all.

- **Real bug, not a hypothetical: `wget`'s healthcheck failed against `localhost` even though the app was already serving traffic correctly.** The frontend's Dockerfile `HEALTHCHECK` used `wget -qO- http://localhost:8080/`, and it failed every single retry ("Connection refused") while `curl http://localhost:3000/` from the host worked fine and `docker compose exec frontend ps` showed nginx up and `netstat` showed it listening on `0.0.0.0:8080`. Root cause: inside the container, `localhost` resolves `::1` before `127.0.0.1` (per `/etc/hosts`), nginx's `listen 8080;` only binds the IPv4 socket, and busybox `wget` — unlike `curl`, which tries every resolved address until one connects — only tries the first address and gives up. Fixed by pointing the healthcheck at `http://127.0.0.1:8080/` explicitly instead of relying on hostname resolution order. Backend's healthcheck uses `curl`, which never hit this because of curl's fallback behavior — so the same "use `localhost` in a container healthcheck" pattern silently works with one tool and silently fails with another, depending only on which client binary happens to be in the base image.

- **Non-root nginx requires more than `USER nginx`.** The stock `nginx:alpine` image's default `/docker-entrypoint.d/` startup scripts assume root (one of them, `10-listen-on-ipv6-by-default.sh`, tried to rewrite `/etc/nginx/conf.d/default.conf` and logged `can not modify ... read-only file system?` — harmless here since our custom `nginx.conf` doesn't reference `conf.d` at all, but a reminder that the base image's own tooling half-expects root). Getting a genuinely non-root, working nginx needed: moving the pid file to `/tmp/nginx.pid` (default `/var/run/nginx.pid` isn't guaranteed writable), binding to port 8080 instead of 80 (ports below 1024 need root), dropping the `user nginx;` directive from `nginx.conf` (meaningless — and noisy — once the whole process already runs as that user, not just its workers), and `chown -R nginx:nginx` on `/usr/share/nginx/html` and `/var/cache/nginx` so the pre-existing `nginx` user (uid 101, already defined in the base image) can actually read/write what it needs. Verified with `docker compose exec frontend id` → `uid=101(nginx)`.

- **Runtime config injection instead of a build-time env var.** The frontend needs to know the backend's base URL, but that URL is only known at `docker compose up` time (the host port), not at image-build time — and baking it into the Vite bundle would mean rebuilding the frontend image every time the port or deployment target changes. Instead, `docker-entrypoint.d/10-generate-config.sh` writes `/usr/share/nginx/html/config.js` (setting `window.__API_BASE_URL__`) from the `API_BASE_URL` environment variable at container *startup*, and `index.html` loads it before the app bundle. This is also what makes the upcoming nginx-reverse-proxy phase a one-line change (`API_BASE_URL=""` → same-origin `/api` calls) instead of a frontend rebuild.

- CORS had to be added on the backend (`CORSMiddleware`, origins from `CORS_ALLOW_ORIGINS`, derived in compose from `FRONTEND_PORT` so it isn't a second hardcoded port) — expected and by design at this phase, since the browser is calling `localhost:8000` directly from a page served on `localhost:3000` (different origin). This requirement goes away once Phase 4's nginx proxies both under one origin, but is correct and necessary for "talking directly to the backend's exposed port" as this phase specifies.

- Not yet visually verified in an actual browser — no browser/screenshot tool is available in this session. Verified instead via: the Vite build completing without errors, the served `index.html`/JS bundle content, `config.js` injection, and hitting every endpoint the UI calls (`/api/links`, `/api/analytics/top-links`, `/api/analytics/clicks-over-time`) directly, including a CORS preflight and a real GET with an `Origin` header. Recommend opening `http://localhost:3000` by hand to click through the form and the chart before signing off on this phase.

## Phase 4 — Nginx reverse proxy + two-network split

- **The plan's routing description ("/ -> frontend, /api -> backend") has no room for short-link redirects, and that's not a nitpick — it's the app's core feature.** A bare `GET /{short_code}` doesn't fit either bucket: it's not `/api/*`, and it's not the SPA either. Routing it to `/` would mean nginx serves the React app's `index.html` for every short link instead of actually redirecting — silently breaking the one thing a URL shortener has to do, the moment nginx gets introduced. Solved with a third `location` in `proxy/nginx.conf`: a regex matching a single path segment of 3-16 alphanumeric characters (matching `LinkCreate.short_code`'s validation and what `_generate_short_code()` produces), checked before falling through to the frontend catch-all. Deliberate side effect worth stating plainly: this reserves all single-segment top-level paths for short codes — if the SPA ever needed its own top-level routes (e.g. `/login`), they'd need an explicit location added above the regex, or they'd get swallowed by it.

- **Real config error: nginx's parser choked on `{3,16}` in an unquoted regex location.** `location ~ ^/[A-Za-z0-9]{3,16}$ {` failed to start with `unknown directive "3,16}$"` — nginx's own config grammar uses bare `{`/`}` as block delimiters, so an unquoted `{` inside a location pattern gets parsed as the start of the location's body, not as part of the regex. Fixed by quoting the whole pattern: `location ~ "^/[A-Za-z0-9]{3,16}$" {`.

- **Removed CORS entirely instead of leaving it configured-but-harmless.** Phase 3 added `CORSMiddleware` because the browser called `localhost:8000` from a page served on `localhost:3000` — genuinely cross-origin. Now that nginx fronts both under one origin, that middleware, its `cors_allow_origins` setting, and the `CORS_ALLOW_ORIGINS` env var are all dead weight — same-origin requests don't even send a preflight. Deleted rather than left in "just in case," since a reviewer finding unused CORS config is exactly the kind of thing that reads as copy-pasted-and-not-understood.

- **Rate limiting would have silently become a global limiter for every real user combined, if left as-is.** `rate_limit_create` kept every visitor from the internet indistinguishable, since `request.client.host` now always resolves to the nginx container's address once nginx is the sole path to backend — one heavy user would exhaust the limit for everyone. Not something the plan calls out explicitly, but a direct, immediate consequence of introducing the reverse proxy that had to be fixed in this same phase, not deferred: nginx now sets `X-Forwarded-For`, and `_client_ip()` prefers that header (taking the first hop) over `request.client.host`. This is only safe to trust because backend no longer publishes a host port at all — the only way to reach it is through nginx (which sets the header truthfully) or another container already on `frontend-net`.

- **Real bug caught before it shipped: the Phase 3 runtime-config fallback treated `""` as "unset."** `window.__API_BASE_URL__ || 'http://localhost:8000'` — but `""` (the value this phase deliberately sets for same-origin mode) is falsy in JS, so the `||` would have silently ignored it and kept calling the old absolute dev URL instead of switching to relative `/api` calls. Exactly the kind of thing that "looks like it still works" if the old backend port happens to still be reachable, then breaks in a real deployment. Fixed to check `!== undefined` instead of relying on truthiness.

- **Only `nginx` (the `proxy` service) publishes a host port now** — `postgres`, `redis`, `backend`, and `frontend` all lost their `ports:` mappings, matching section 3's "only Nginx publishes a port to the host" exactly. `docker compose ps` now shows bare container ports (`8000/tcp`, `5432/tcp`, etc., no `0.0.0.0:` prefix) for everything except `proxy`. `POSTGRES_PORT` was kept in `.env` (unused in the base compose file) specifically because Phase 5's override file will need it again for local `psql` access — not dead config, just not wired up yet.

- **Confirmed, not assumed: the frontend container cannot reach Postgres or Redis.** `docker inspect` shows `frontend` and `proxy` attached only to `frontend-net`; `postgres` and `redis` attached only to `backend-net`; `backend` attached to both (as the plan requires — it's the only bridge). From inside the frontend container: `wget http://postgres:5432` failed with `bad address` (DNS resolution itself fails — there's no route to look up, not merely a blocked one), and even connecting directly to Postgres's real `backend-net` IP address (bypassing DNS entirely) timed out — no path exists between the two networks. As a positive control, the same style of request from `backend` (which *is* on `backend-net`) succeeded (curl exit 52, "empty reply from server" — a real TCP connection, just not talking HTTP), proving the isolation is specific to the network topology, not some general connectivity fault.

- End-to-end through the single published port (80) only: SPA loads, `POST /api/links`, `GET /{short_code}` redirect, and both analytics endpoints all work purely through nginx, with every other service unreachable from the host.

## Phase 5 — dev/prod compose split, seed script

- **`GET /health` and a short link with `short_code="health"` would collide — and it turns out FastAPI's own route registration order is what quietly prevents that from mattering.** Discovered while sanity-checking `/health` through the proxy: nginx's short-code regex (`^/[A-Za-z0-9]{3,16}$`) matches `/health` too (6 alnum chars), so nginx forwards it to the *same* backend upstream as any other short code would go to — nginx itself doesn't distinguish "this is the health check" from "this is a redirect." What actually resolves it is that `main.py` includes `health.router` *before* `links.redirect_router`, and Starlette matches routes in registration order, so the literal `/health` route wins over the parameterized `/{short_code}` route regardless. Consequence worth documenting rather than leaving implicit: a link with `short_code="health"` (or any other name colliding with a real backend route added later) would be permanently unreachable via redirect — silently shadowed by the literal route. Not fixed, since fixing it would mean either reserving certain codes at creation time or moving health under `/api`, both bigger changes than this phase's scope — documented instead so it doesn't look like an oversight.

- **The dev-mode frontend needed its own `HEALTHCHECK`, and it couldn't reuse the prod one.** `docker-compose.override.yml` points the frontend service at the Dockerfile's `build` stage (`target: build`) instead of the final nginx-based `runtime` stage, so it can run `npm run dev` for hot reload. But Docker image metadata like `HEALTHCHECK` is stage-local — the `runtime` stage's healthcheck (probing nginx on 8080) doesn't carry over, and that stage doesn't exist yet at `target: build`. Without a healthcheck at all, `proxy`'s `depends_on: frontend: condition: service_healthy` would refuse to start. Fixed by adding a second `HEALTHCHECK` directly in the `build` stage, probing Vite's dev server on 5173 instead — added measure: since each Docker stage's instructions are independent unless copied forward with `--from=`, this has zero effect on the production image.

- **Known, accepted limitation: in dev mode, nginx's own `/` route to the frontend stops working.** `proxy/nginx.conf`'s upstream always points at `frontend:8080`, but the dev override replaces the frontend container's whole process with Vite's dev server on port 5173 — nothing is listening on 8080 anymore while the override is active, so hitting the proxy's port 80 for `/` would 502. This is intentional, not overlooked: dev-mode frontend work happens via `http://localhost:5173` directly (with HMR), and `docker-compose.prod.yml` is what restores nginx's `/` route to something real. Documenting this explicitly so it doesn't get "fixed" by accident later in a way that reintroduces complexity this phase deliberately avoided.

- Extended `vite.config.js`'s dev-server proxy to cover both `/api` and the same short-code regex nginx uses, so clicking a link in the table behaves identically whether you're using `npm run dev` (port 5173) or the full stack (port 80) — verified both a `POST /api/links` and a `GET /{code}` redirect through the Vite dev server directly.

- Simplified the frontend's `API_BASE_URL` fallback once the Phase 4 CORS removal made the old absolute-URL dev default (`http://localhost:8000`) actively wrong — that port isn't published anywhere anymore in any run mode. Relative (`''`) is now correct everywhere (nginx in prod, Vite's own proxy in dev), so the fallback collapsed to a single `?? ''`.

- Verified both compose modes independently: `docker compose -f docker-compose.yml -f docker-compose.prod.yml up` (no override — confirmed via `docker inspect` that `HostConfig.Memory`/`NanoCpus` actually reflect the configured limits, and Postgres has no host port), and plain `docker compose up` (override auto-loaded — confirmed hot reload with a real edit to `health.py`, watched `WatchFiles detected changes ... Reloading...` in the logs, and confirmed Postgres's port is reachable from the host via `pg_isready`).

- `seed.py` checks `db.query(Link).count() > 0` before inserting anything, so re-running it against an already-seeded database prints a message and exits instead of hitting the `short_code` unique constraint. Verified: first run seeded 5 links/140 clicks with a nicely shaped "top links" ranking and a multi-day `clicks-over-time` series; second run correctly skipped.

## Phase 6 — README + design decisions

- **Real bug found while writing the README's own "how to open the docs" line, not while coding a feature.** Went to document `http://localhost/docs`, tested it first rather than assuming, and found `/docs` returned 200 but `/openapi.json` returned 200 with `content-type: text/html` — it was silently serving the frontend's `index.html` instead of the OpenAPI schema. Cause: `openapi.json` contains a `.`, which isn't in `[A-Za-z0-9]`, so it doesn't match the short-code regex at all and was falling through to the frontend SPA catch-all. Swagger UI at `/docs` loaded its shell fine (that request matched `/docs` exactly, which happened to also match the short-code regex by coincidence — 4 alnum chars) but would have failed to render any actual API schema. Fixed with three explicit `location = /docs`, `location = /redoc`, `location = /openapi.json` blocks in `proxy/nginx.conf` (exact-match locations are checked before any prefix or regex location in nginx, so these are unambiguous regardless of the short-code regex). Verified `/openapi.json` returns real `application/json` content after the fix. A good reminder that "write the README" is still a verification step, not just a writing task — every claim in it got tested against the running stack before being written down as fact.
